## Rehearsal results and repairs

A disposable PostgreSQL **17.11** cluster used distinct directly authenticated
`regengine_migrator`, `regengine`, and `regengine_sysadmin` logins. All three
had no superuser, BYPASSRLS, CREATEDB, CREATEROLE, replication, or membership
capabilities. The migration login owned the scratch database. Provider access
created roles and seeded synthetic rows only. Supabase-style `anon` and
`authenticated` roles were present.

The source database reached `267d8053ced5`, then received two tenants, two
users, five audit entries, three CTEs, one request case, and two signoffs.
`scripts/backup_postgres.sh` created a plain SQL/gzip dump; `psql` restored it
into a **separate empty database as the restricted migration owner**. Counts
matched before upgrading. This is an actual dump/restore of a synthetic
fixture, not an approved production backup or a recovery-time commitment.

The restored database now reaches **`c6a120b4e901`** through
`scripts/run-migrations.sh`; a second invocation succeeds. The six seeded
tables preserve their row counts. The five audit rows acquire per-tenant
sequences and both legacy users acquire passwordless email identities.
The seeded v079 regression also verifies non-null email fingerprints with a
synthetic HMAC secret. No real passwords or production data were used.

Repairs covered by the rehearsal:

- v116 and v120 temporarily remove **FORCE** RLS only from the two rule tables
  whose owner must backfill data. RLS remains enabled; policies are unchanged.
  Forced posture is restored before the migration transaction commits. On
  failure PostgreSQL rolls back both the DDL and data. Table locks prevent
  concurrent sessions from observing the temporary owner access.
- v084 temporarily removes FORCE from legacy `users` during its owner-only
  identity backfill. Previously a restricted owner silently saw zero users,
  so the chain could succeed while losing passwordless identities.
- The managed v111 rerun now preserves the later v113 invite lookup grant
  for the admin role only. Ordinary runtime execution and invite-table reads
  remain denied; the original broad function grant is narrowed in v113 too.
- Six real-PostgreSQL rule migration tests cover successful audit writes,
  injected audit failures with data/posture rollback, and runtime-role denial.
  The seeded fixture tests both pinned v079 and v089 histories in hosted CI,
  each with and without Supabase-style client roles.
- Migration sessions use UTC and `search_path=public,fsma,extensions` so the
  existing `pgcrypto` functions resolve. Production must verify its trusted
  schemas and actual migration login independently.

Local acceptance is distinct from hosted checks for the final pushed SHA.
The approved production backup, provider extension ownership plan, restored
production-state role checks, and production recovery timing remain
**not verified**. No production migration was executed.

## Stop and recovery conditions

Stop on ownership/policy drift, unexpected data changes, missing backup proof,
timeout, failed migration, or failed canary. Capture the actual Alembic revision
after failure: do not assume the entire chain rolled back as one transaction.
Never stamp past a failed migration or disable the runtime posture gate.

v088 destroys legacy password material and v091 removes duplicate signoffs;
an Alembic downgrade does not restore that data. Recovery requires the tested
backup/restore path and a compatible application artifact while writes remain
paused. Returning to the currently observed RLS-disabled posture is not an
accepted release rollback. Keep service unavailable if no verified safe
artifact/database pair exists.
