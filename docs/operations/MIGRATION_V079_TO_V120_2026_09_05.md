## Rehearsal results and required repairs

A disposable PostgreSQL 16.14 cluster used distinct directly authenticated
`regengine_migrator`, `regengine`, and `regengine_sysadmin` logins. All three
had no superuser, BYPASSRLS, CREATEDB, CREATEROLE, replication, or membership
capabilities. The migration login owned the scratch database. Provider access
created roles and seeded synthetic rows only. Supabase-style `anon` and
`authenticated` roles were present.

The chain reached `267d8053ced5`, then seeded two tenants, two users, five
audit entries, three CTEs, one request case, and two signoffs. The existing
`tests/migrations/seed_mid_chain.sql` fixture needed a disabled synthetic
password value because v079 still requires `users.password_hash`; no real
passwords or production data were used.

1. With the default local search path, `scripts/run-migrations.sh` failed at
   receipt revision `c1d2e3f4a5b6`: `function digest(text, unknown) does not
   exist`. Earlier migrations had installed `pgcrypto` in `fsma`. Retesting
   with a migration-session search path of `public,fsma,extensions` passed
   that point. This is a local reproduction and a deployment precondition;
   the live connector already sees `extensions`.
2. That retest failed at `e4a7c2d91b06`, v116, inserting the harvester-phone
   rule: `new row violates row-level security policy for table
   "rule_definitions"`. The error is reproduced with the intended restricted
   owner. The earlier superuser-based local checks did not cover this case.
3. **No successful v079-to-head, managed rerun, or row-preservation result is
   claimed.** The failed rehearsal does not validate v120's rule updates
   under forced RLS either. The current v120 unit migration test explicitly
   omits RLS; add direct-owner evidence for both revisions.

Before retrying, prepare a narrow, separately reviewed migration repair for
the v116 rule-data operation and verify v120 under the same owner. Preserve
rule/evaluation history, audit entries, and final forced-RLS posture. Do not
make the migration login a superuser or grant it BYPASSRLS. A new migration
after head cannot repair an earlier migration that prevents reaching head.

## Stop and recovery conditions

Stop on ownership/policy drift, unexpected data changes, missing backup proof,
timeout, failed migration, or failed canary. Capture the actual Alembic revision
after failure: do not assume the entire chain rolled back as one transaction.
Never stamp past a failed migration or disable the runtime posture gate.

v088 destroys legacy password material and v091 removes duplicate signoffs;
an Alembic downgrade does not restore that data. Recovery requires the tested
backup/restore path and a compatible application artifact while writes remain
paused. Returning to the currently observed RLS-disabled posture is not an
accepted release rollback. Keep service unavailable if no verified safe
artifact/database pair exists.
