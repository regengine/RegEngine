# Reliability and scaling assessment

**Date:** 2026-08-31. **Classification:** docs-only research, production-spine scope. **Conclusion:** the checked-in application has useful transactional safeguards, but its first credible scaling limits are tenant-serialized writes, synchronous exports over an entire tenant history, and shared database/process resources. Event volume alone cannot establish customer capacity. No live configuration, hardware allocation, database size, latency, throughput, load test, backup, or recovery target was verified.

## What actually runs

The deployment configuration selects the root Dockerfile. It runs migrations and then a consolidated FastAPI application with four Gunicorn/Uvicorn worker processes by default, a 120-second worker timeout, and 30-second graceful shutdown (`railway.toml:1`, `Dockerfile:89`). Each application process starts the older task processor plus the shared ingestion task worker (`server/main.py:113`). The frontend ingestion proxy has a checked-in 60-second function duration (`frontend/vercel.json:17`). These are configuration facts, not evidence that production currently uses these defaults; the timeout values are not interchangeable end-to-end latency guarantees.

PostgreSQL is required by readiness; configured Redis or Neo4j failures also affect readiness (`server/main.py:593`, `server/main.py:642`). Readiness proves connection reachability, not queue progress, representative query speed, evidence completeness, or successful export. A newly created database engine and connection are used for each PostgreSQL readiness probe.

The shared PostgreSQL pool defaults to 10 persistent plus 20 overflow connections per process and a 30-second acquisition timeout (`services/shared/database.py:103`). A separately configured PostgreSQL admin engine also defaults to 10 plus 20 (`services/admin/app/database.py:101`). With both engines configured, four processes permit a **theoretical client-side ceiling of 240 connections per container**, before other engines, probes, deployment overlap, or replicas. This is neither measured usage nor the database's allowed connection count. Transaction poolers can change the relationship between client and server connections. Two overlapping containers double the configured client-side ceiling; adding workers requires an explicit database connection budget.

## Write behavior and concentration risk

Webhook batches contain 1–500 events (`services/ingestion/app/webhook_models.py:232`). The handler validates, performs legacy batch persistence, then persists a canonical record and rule evidence synchronously for each accepted event before committing the request transaction (`services/ingestion/app/webhook_router_v2.py:1405`, `services/ingestion/app/webhook_router_v2.py:1425`, `services/ingestion/app/webhook_router_v2.py:1561`). Required canonical failure propagates, and the outer exception path rolls back. “Accepted” is therefore intended to represent committed evidence, not a promise to eventually process an in-memory queue.

Both writers acquire a transaction-scoped advisory lock derived from the tenant ID (`services/shared/cte_persistence/core.py:355`, `services/shared/canonical_persistence/writer.py:85`). This protects chain growth, including the first event, but serializes concurrent writes for one tenant until transaction end. A larger batch amortizes some SQL overhead while extending the time other requests for that tenant wait. Event inserts are chunked by 50, but chain entries are still inserted individually; canonical persistence and rule evaluation also occur per event (`services/shared/cte_persistence/core.py:985`, `services/shared/cte_persistence/core.py:1124`). “Batch” does not mean one database operation.

For batch size **B** and measured lock-held duration **L(B)** seconds, one tenant's optimistic write ceiling is **B/L(B)** events/second. Actual sustainable throughput must be below that ceiling to leave room for variance and recovery. Illustratively, effective lock time of 1, 10, or 50 milliseconds/event implies ceilings of 1,000, 100, or 20 events/second. **All three latencies are unmeasured scenarios.** Network round trips, rules, indexes, contention, and commit flush can dominate hashing.

The default webhook allowance is 120 requests/minute/tenant (`services/ingestion/app/webhook_router_v2.py:465`). Its intended average admission ceiling is **2B events/second**, so one-event requests differ radically from 500-event batches. At one event/request, 1,000,000 events/day for a single tenant exceeds that allowance even before capacity is considered. Ten thousand tenants sending 100/day create the same aggregate daily volume with different auth, request, cache, and connection costs. The Redis limiter uses a separate count and add sequence, so concurrent admission can overshoot; its in-memory fallback is per process (`services/shared/tenant_rate_limiting.py:72`). Treat the allowance as an operational control, not a precise capacity measurement.

**EPCIS does not share the webhook's required canonical-write guarantee.** Independent source inspection confirms its canonical/rule work runs in a daemon thread using the caller's same `db_session`; the caller joins for five seconds by default, then merely logs a still-running thread or captured exception (`services/ingestion/app/epcis/persistence.py:783`, `services/ingestion/app/epcis/persistence.py:803`, `services/ingestion/app/epcis/persistence.py:843`). The single-event wrapper subsequently commits and closes that session (`services/ingestion/app/epcis/persistence.py:921`). Despite the nearby “already committed” comment, that wrapper's commit occurs afterward. The timeout does not cancel the thread: database slowdown can produce overlapping session use, growing unfinished work, or canonical/rule evidence missing from successful legacy acceptance. A legacy-idempotent retry skips this canonical block (`services/ingestion/app/epcis/persistence.py:787`), so ordinary replay is not demonstrated to repair divergence. This is a code-supported failure mechanism, not a reproduced incident. Test delayed and failed canonical writes plus retries before counting EPCIS successes as complete evidence or increasing its concurrency.

## Transparent six-level demand model

The unit is an **accepted CTE event**, not a customer, document, API call, or rule evaluation. Let **D** be events/day. Normal demand is **D/86,400**; the burst scenario is **10D/86,400**. A separate recovery scenario replays one day's missing arrivals in 15 minutes: **D/900**, *in addition to ongoing demand*. This is roughly 96 times the daily average, illustrating why daily averages obscure importer and recovery pressure.

Assume **8 KiB of effective retained database storage/event**, including a provisional allowance for legacy/canonical rows, KDEs, chain, rule evidence, and indexes. This is **unmeasured**, not a schema-derived size estimate. At 730 days, storage is **D × 730 × 8,192 / 2³⁰ GiB**. The 730-day horizon is a modeling assumption, not verification of the legal or implemented retention policy. Source files, attachments, object storage, replicas, backups, WAL, logs, bloat, and export artifacts are excluded.

The final column is arithmetic **ceil(D/10,000)** for a hypothetical one-day full export, not an implemented pagination API or guaranteed result bound. A 2–32 KiB storage sensitivity makes every storage figure **0.25–4×** the baseline. At one million/day that is approximately **1.36–21.76 TiB** after 730 days before excluded copies and artifacts. No machine specification is assumed; these are demand and storage calculations, not claims of linear scalability.

At 10–1,000/day, correctness, onboarding and dependable export remain the appropriate focus. At 10,000/day, full-day exports reach the seed cap. At 100,000/day, retention and recovery already warrant measured query plans and lock timing. At one million/day, modest average demand coexists with large retention and burst demands. These are investigation thresholds, not proven breakpoints.

## Export work grows with history

`/export/all` requires dates within a 90-day window and initially reads at most 10,000 events. It then queries each distinct TLC separately; the outer grouping into 50 TLCs does not issue one SQL query for the group (`services/ingestion/app/fda_export/router.py:538`, `services/ingestion/app/fda_export/router.py:564`). TLC queries can traverse transformation links to five hops, fetch every matching event, and query KDEs in chunks of 100 (`services/shared/cte_persistence/core.py:1273`, `services/shared/cte_persistence/core.py:1330`, `services/shared/cte_persistence/core.py:1376`). Shared transformation neighborhoods can be fetched repeatedly before deduplication. Initial filtering therefore does not provide a strict memory or output-row bound.

More consequentially, both TLC and full exports verify the **entire tenant chain**, even for a narrow date range (`services/ingestion/app/fda_export/router.py:294`, `services/ingestion/app/fda_export/router.py:609`). Chain verification performs an ordered `fetchall()` over tenant history plus a count of accepted legacy records (`services/shared/cte_persistence/core.py:1541`). If a tenant retains **H** events and requests **F** exports, this component repeatedly processes approximately **F × H** chain rows; it is not bounded by the export window. An illustrative Python footprint of 0.5–2 KiB/chain row means one million chain rows alone occupy roughly 0.48–1.91 GiB. **Those byte sizes are unmeasured** and exclude CSV, event dictionaries, packages, and runtime overhead.

CSV and ZIP output are generated in memory before `StreamingResponse` wraps the completed content (`services/ingestion/app/fda_export/router.py:607`, `services/ingestion/app/fda_export/router.py:710`, `services/ingestion/app/fda_export/router.py:761`). Synchronous SQL inside these async handlers can occupy an API worker's event loop. Concurrent exports therefore compete with ingest and readiness. When the initial count exceeds 10,000, the route returns an `X-Truncated` header rather than a complete tenant dump (`services/ingestion/app/fda_export/router.py:692`). Clients must not mistake a downloaded file for complete evidence.

## Degradation, retries, and retention

An unavailable export audit write halts export instead of returning unaudited evidence (`services/ingestion/app/fda_export/router.py:627`). That is the right integrity preference but makes export availability depend on database writes. No durable export-job handoff exists in these handlers. A disconnected or timed-out client may retry and recompute the entire artifact; success of a server audit entry does not prove client receipt.

The database circuit/bulkhead wrapper protects `get_db`, but the webhook uses the separate plain `get_db_session` dependency and export directly creates `SessionLocal` (`services/shared/database.py:120`, `services/shared/database.py:172`, `services/ingestion/app/fda_export/router.py:558`). Do not credit every route with the wrapper's retries or bulkhead. Database degradation lengthens transaction/lock waits and can exhaust connections before it becomes a clean outage. Ingest rejects unavailable persistence rather than buffering accepted events locally. Clients need bounded backoff and stable idempotency keys; retry correctness belongs in the concurrent and ambiguous-commit experiments below.

Redis failure has mixed behavior: rate limiting falls back locally, but paid webhook subscription verification fails closed with 503 (`services/ingestion/app/subscription_gate.py:150`). Graph sync is disabled by default and bounded when enabled; it is not the durable primary evidence store (`services/ingestion/app/webhook_router_v2.py:1101`).

The shared task worker polls every two seconds, reclaims expired claims, and retries failures before marking tasks dead. Its default lease is 300 seconds, with no heartbeat in this implementation (`services/shared/task_queue.py:493`, `services/shared/task_queue.py:585`, `services/shared/task_queue.py:762`). A slow handler may execute again after lease expiry. A separate ownership concern exists: startup supplies no task-type allowlist, while unknown types are marked dead; the older processor has its own `nlp_extraction`/`review_item` registry (`server/main.py:131`, `services/shared/task_queue.py:631`, `services/shared/task_queue.py:701`, `server/workers/task_processor.py:141`). This is a static secondary-path finding, not a reproduced production incident.

For queued secondary work arriving at **λ tasks/second**, an outage lasting **O seconds** creates approximately **λO** waiting tasks, provided producers can still persist them. With recovery service rate **μ**, ideal drain time is **λO/(μ−λ)**, and recovery never catches up when **μ≤λ**. Retry amplification, leases and contention make actual recovery slower. This queue model does not apply to synchronous webhook acceptance or the current export handlers; those depend on client retries when unavailable.

Cleanup jobs exist for completed/dead tasks and older records (`services/scheduler/main.py:587`, `services/scheduler/main.py:683`, `services/scheduler/main.py:918`), but this scheduler is not started in the inspected monolith lifespan. Actual execution is **not verified**. The archival method shown deletes legacy CTE records and export records; it does not demonstrate an archive destination or coordinated canonical/chain retention. Do not assume storage plateaus or that deletion preserves audit verification. Backup restore and recovery objectives remain unverified.

## Falsifiable next experiments

Use an isolated disposable PostgreSQL/Redis environment with synthetic tenant data; record hardware, DB connection cap, versions and settings. No production load is justified by this report.

1. **Write concentration:** compare batches of 1/50/500 across 1/10/100 tenants at the modeled normal, burst and replay rates. Measure lock duration, p50/p95/p99 latency, event-loop delay, connection waits and committed events/s. Fail on missing evidence, duplicate chain membership, inconsistent response counts, or sustained backlog growth.
2. **Export history:** hold requested output at 1,000 events while increasing tenant history from 10,000 to one million; separately increase TLC fan-out and concurrent exports. Record peak RSS, SQL count, wall time, rows, truncation detection and ingest latency. This directly tests history-dependent cost and resource interference.
3. **Failure recovery:** interrupt DB connections before/after commit, delay EPCIS canonical writes beyond five seconds, exhaust a small connection budget, stop Redis, disconnect an export client, and restart workers mid-handler. Retry the same idempotency key; reconcile legacy/canonical/rule/chain evidence. Test a handler longer than 300 seconds and mixed queue types. Check duplicate effects and dead-task handling, not merely HTTP status.
4. **Retention and restore:** measure table/index/WAL bytes per accepted event after representative rule outcomes; restore a backup and verify counts, chain and export completeness. Demonstrate scheduler ownership and legal-hold behavior before enabling deletion. Define and measure recovery objectives before selling an availability promise.
