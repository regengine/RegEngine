# RegEngine OKR — May 13 2026 → end of Q2

**Decision date:** 2026-05-13
**Owner:** Christopher Sellers (solo technical founder)
**Status:** Active

## The OKR

> **N pilot operators with ≥1 real CTE event ingested in the past 7 days.**

Single metric. Weekly cadence. Read on Mondays from a query against the production `cte_events` table (or equivalent) joined to `tenants`, counting distinct tenants with `event_time >= now() - interval '7 days'`.

Initial target: **N = 1** by end of May 2026 (i.e., one real pilot ingesting any CTE event, even synthetic-but-pilot-owned). Then **N = 3** by end of June 2026.

## Why this metric

A real CTE event from a real pilot proves the whole chain works: account creation, login, API key issuance, signed authentication, ingestion endpoint, validation, persistence, RLS scoping. Anything less proves a subset.

Alternatives considered and rejected:

- **Pilots running monthly recall drills.** Drills are the strongest product surface but fire too infrequently (monthly) to give a useful weekly signal during pilot acquisition.
- **Signed pilot LOIs.** Measures intent, not usage — and is easier to game than usage data. Useful for fundraising, not for engineering decisions.
- **API-key count or signup count.** Vanity metrics. Many signups, zero usage is worse than three signups with three weekly active users.

## How decisions route through this OKR

Every engineering decision, audit pass, copy sweep, or refactor must answer: **"Does this make it more likely that a pilot will ingest a CTE event this week, or more likely they'll keep doing so next week?"** If the answer is no, defer.

Explicit examples of what passes:

- Fixing onboarding friction observed in a real pilot session (passes).
- Provisioning Cloudflare R2 so `/v1/ingest/url` works (passes — currently 503 per #2349).
- Wiring Resend SMTP so signup confirmation emails reach pilots (passes).
- A pilot-onboarding self-serve flow (passes).
- A CTE-freshness dashboard the founder watches each Monday (passes).

Explicit examples of what defers:

- New internal audit pass with no specific pilot-reported issue (defers).
- Refactoring a service module for "code health" without a measurable pilot impact (defers).
- T&S copy sweeps beyond what existing lint gates catch automatically (defers).
- Closing inactive meta-epics (they're already closed as of 2026-05-12, but the principle stands).

## Operational ratchet

- **Monday morning, weekly:** founder reads the count. If the count moves, write a one-line note on what moved it. If it doesn't move, the next decision must directly target moving it.
- **Once a pilot is live:** schedule a 30-minute observation session every two weeks. Watch them use the product without interjecting. Take notes. The notes drive the next sprint, not the audits.
- **First pilot acquisition:** pick one warm contact from the 200+ outreach list (`docs/research/fsma-204-go-to-market-2026-05.md`, May 6 memo). Send a calendar invite. Don't optimize the onboarding flow until that first session has happened.

## What this OKR explicitly does NOT cover

- Revenue. Pilots may be free or paid; the metric counts usage either way.
- Code quality. Maintained at a "doesn't regress what works" floor, not optimized.
- Audit completeness. The current audit posture (closed meta-epics, 503-gated unconfigured paths, active CI lints) is sufficient until a pilot finds an issue.
