83:def _normalized_dict_detail(status_code: int, detail: dict) -> dict:
84:    """Give every client-error envelope a ``type`` and a ``message`` (#2863).
85:
86:    ``HTTPException(detail={...})`` used to be forwarded verbatim, so the
87:    ~70 call sites that pass a dict each defined their own envelope. Three
88:    incompatible shapes reached clients: ``{"type", "message", "details"}``
89:    from the RequestValidationError handler, ``{"type", "message"}`` from a
90:    string detail, and the raw dict from a dict detail — which commonly
91:    carries ``code`` where the others carry ``type``. A client could not use
92:    one code path for all errors, and the published spec matched none of them.
93:
94:    Every original key is preserved, so callers reading ``code``, ``errors``
95:    or any bespoke field keep working; this only guarantees that ``type`` and

97:    ``code`` (the common alternative spelling), then ``http_<status>``.
98:    """

104:    # of the bespoke shapes are unaffected.
