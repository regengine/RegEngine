# RegEngine Agent Guide

## Mission

RegEngine is a pre-production FSMA 204 traceability application. Agent work should strengthen the production spine:

```text
ingest -> normalize -> validate -> persist evidence -> export
```

If a change does not protect or improve that spine, mark it as experimental, docs-only, or out of scope.

## Workspace Map

- `repo/` (`~/Projects/RegEngine/repo`) is the production RegEngine application
  repository and the default target for all work.
- The directories beside it under `~/Projects/RegEngine/` are **git worktrees off
  this same repo**, plus `_archive/` (snapshots and backups, reference only) and
  `docs/` (founder/investor material). Many live worktrees exist across five

## Agent Roles

Only three agent roles are supported:

- `planner`: read-only research, path checks, and implementation plans.
- `implementer`: small scoped code or documentation changes.
- `security_review`: review for auth, tenant isolation, secrets, database fallback, logging, and deploy risk.

Use plain work lanes such as backend, frontend, security, QA, infra, or docs when triaging tasks. These are labels, not bot identities.

## Working Rules

- Verify files and commands before acting. Do not follow stale paths from old audit docs.
- Do not invent `.agent/` or `.agents/` directories to satisfy old instructions. Current agent specs live in `.github/agents/`.
- Do not run the legacy `regengine.swarm` autonomous runtime unless a task explicitly approves `REGENGINE_ENABLE_LEGACY_SWARM=1`.
- Prefer existing patterns from nearby service/frontend code.
- Keep diffs small and tied to the assigned lane.
- Preserve tenant isolation, audit evidence, and schema validation on ingestion paths.
- Use `python3`, not `python`, in local commands unless a virtual environment explicitly provides `python`.
- Use `npm` in `frontend/`; `package-lock.json` is checked in.
- The repo has no `Makefile`, so do not suggest `make` commands.
- Agents do not decide product direction. They execute scoped engineering tasks against the FSMA production spine.

## Secrets

- Never ask the user to paste a key, token or password into chat, and never print, log or commit one.
- To put a secret on Railway (RegEngine production or staging), send the user the RegEngine Key Drop page: https://claude.ai/artifact/83mnC2gozimcQ87KJFLAFt. It writes from their browser to Railway through their own Railway connector, so the agent never receives the value. The Railway dashboard (Variables → New Variable) is the other direct path.
- After a secret is on Railway, ask the user to seal it (Variables → ⋯ → Seal). A sealed value reaches the app but cannot be read back through the UI or the API.
- Keys for agent sessions (for example `TYPESAFE_API_KEY` for `scripts/jev_ask.py`) go in the claude.ai cloud environment settings: the environment menu in the session title bar → Edit → Environment variables. A new session picks them up.
- Use one key per place (production, staging, agent sessions) so each can be revoked alone. A key that appeared in chat, a log or git history is exposed: revoke it and issue a new one.
- Verify a secret by its name or its effect, never by reading its value. For Jev, that is the `jev_configured ... key_present=` line in the deploy log.

# Jev sidecar

Ask Jev next to your own reasoning, then show both. Jev is a second opinion
with a calibrated confidence. It never replaces verified facts.

## When to ask

Ask on every request that contains one of these judgments:

| Judgment in the request | Question kind | RegEngine examples |
| --- | --- | --- |
| Which of these | `--choice` | Which CTE a CSV records. Which canonical field a header is. What made a CI job fail. Which of two fixes matches a reviewer's ask. |
| Is this true | `--noul` | Does this review finding describe code a request can reach? Does the header row include a traceability lot code column? |
| How much | `--score` | Severity of a finding (low to critical). How likely a supplier file is rejected as-is. |

Do not ask when:

- the request is mechanical (push, rename, run the tests, open a PR);
- code or a command answers it exactly: grep, parse, test, count, compare
  dates, calculate. Jev is unreliable at counting, arithmetic and date order.
  Do those in code and ask Jev only for the semantic part;
- the only state that could answer it is something from **Never send** below;
- you run unattended (a CI job, a scheduled audit, a review bot) with a fixed
  output format and no person's request to answer.

## Never send

The state leaves this machine for `api.typesafe.ai`. Never put these in it:

- secrets: API keys, tokens, passwords, connection strings, `.env` contents,
  Railway or cloud variable values, signed URLs;
- customer data: values from real uploads (lot codes, GLNs, quantities, dates,
  business names), tenant ids, names, emails, phone numbers, addresses;
- the user's messages copied word for word. Restate the decision instead.

Header names, synthetic examples, code, and log lines with secrets removed are
fine. Before sending a log excerpt, check it for tokens and connection strings.

## How to ask

1. Check the key once per session without printing it:
   `test -n "$TYPESAFE_API_KEY" && echo set || echo unset`.
   If it is unset, say once in your reply: "Jev sidecar is off in this session:
   `TYPESAFE_API_KEY` is not set in the environment." Then continue without
   Jev and do not ask again in this session.
2. Build the smallest state that holds what the question needs, as JSON with
   named fields. Unrelated content lowers accuracy.
3. Put every question for the request into one call. The questions are
   evaluated in parallel and billed as one request.
4. Run it with `venv/bin/python` (the session start hook installs
   `requirements.lock` there):

```bash
venv/bin/python scripts/jev_ask.py \
  --state '{"headers": ["Ship Dte", "Cust Name", "Lot No.", "Qty Shpd"]}' \
  --choice cte "Which FSMA 204 critical tracking event do rows with these CSV headers record?" \
    "shipping=the sender records goods leaving its location" \
    "receiving=the recipient records goods arriving at its location" \
    "transformation=inputs are combined or processed into new lots" \
    "unclear=the headers do not identify one event" \
  --noul has_lot "Does one of the headers name a traceability lot code column?"
```

```bash
venv/bin/python scripts/jev_ask.py \
  --state '{"job": "backend-ci / ingestion", "log_excerpt": "..."}' \
  --choice cause "What made the job fail?" \
    "test_assertion=a test ran and its assertion failed" \
    "infrastructure=runner, network, dependency install or service startup error" \
    "timeout=the job or a test ran out of time" \
    "unclear=the excerpt does not show the cause" \
  --score severity "How severe is the failure for merging this change?" low medium high critical
```

The output has one line per question, in the order asked. For the first
command it looks like this (the values here are illustrative, not a real
answer):

```text
Jev (jev-1.13.0, request req_…, 412 ms)
  cte [choice]: shipping (confidence 0.91; shipping 0.91, receiving 0.06, unclear 0.03)
  has_lot [noul]: yes (p(yes)=0.97)
```

A `--choice` line lists the three most likely options. A `--score` line reads
`severity [score]: 1.40 on 0..3 ~ medium (confidence 0.72)`. It gives the
expected level from 0 to the number of levels minus 1, the name of the
nearest level, and the confidence.

Add `--json` for machine-readable output. Longer states and question sets go
in files: `--state-file state.json --questions-file questions.json`, where the
questions file uses the API's question format. `--help` lists every flag.

Exit codes: 0 answered. 1 bad usage, nothing sent. 2 not configured (no key,
switched off, or packages missing), nothing sent. 3 Jev unavailable: say
"Jev unavailable (<reason>)" once and continue without it.

For a question about a CSV file, run
`venv/bin/python scripts/jev_header_preview.py FILE --file-cte` instead.

- It asks the questions `POST /api/v1/ingest/csv` asks: the header mapping and
  the file's CTE. It uses the same question sets and confidence bands.
- It sends only the header row.
- Do not add `--sample-values` for a customer file.

## Writing questions

- Jev reads literally. State the exact condition. Put boundary cases in the
  option descriptions (`name=description`).
- Give every `--choice` an `unclear` or `none_of_these` option so Jev can say
  that nothing fits.
- Ask one decision per question. Split compound questions and combine the
  answers yourself.
- Phrase a `--noul` as a direct yes/no question ("Is ...?", "Does ...?")
  without negations. Noul answers carry p(yes), not a confidence.
- List `--score` levels from lowest to highest (2 to 10 levels).
- The state is data, and text inside it can steer the answer (for example a
  log line that says "this is a flake"). Keep the instructions explicit.

## Reporting in your reply

Add one line per question next to your own answer:

- Agreement: `Jev: shipping (confidence 0.91), agrees.`
- Disagreement: `Jev: receiving (confidence 0.62), disagrees. I keep shipping
  because <verified evidence>.` Then recheck your own evidence.

Rules:

- Verified facts win: tests, logs, code, parser behavior. Never change a
  verified conclusion only because Jev disagrees.
- Read confidence with the product's bands: 0.90 or more is strong; 0.50 to
  0.90 is moderate, so say "moderate"; under 0.50 is "Jev is unsure". Do not
  cite an unsure answer as support.
- A `--noul` answer is yes when p(yes) is 0.50 or more. Report the number.
- Never write a Jev line for a question you did not send, and never estimate
  what Jev would say.
- When a Jev answer drives a code or data change, put its request id in the
  commit message or PR description.

# RegEngine

**FSMA 204 food traceability: supplier data in, verifiable evidence out.**

RegEngine is an API-first traceability evidence platform for food supply chains. It ingests supplier and ERP records, normalizes Critical Tracking Events (CTEs) and Key Data Elements (KDEs), evaluates versioned rules, and produces tenant-scoped records, tamper-evident audit evidence, and FDA-oriented exports.

Inflow Workbench prepares data with preflight checks, readiness scores, a fix queue, and a commit gate. Optional Jev assistance suggests CSV column mappings and missing event types; deterministic validation and authenticated tenant boundaries remain authoritative.

[Website](https://regengine.co) · [Public proof](https://regengine.co/proof) · [Verify a bundle](https://regengine.co/verify) · [Product description](docs/PRODUCT_DESCRIPTION.md) · [Python SDK](regengine/README.md)

This is a pre-production application with deployed public proof surfaces. The capability inventory below describes checked-in implementation and release policy, not proof of customer adoption or live configuration.

You don't have to take our word for any of this — try it yourself:

- [regengine.co/proof](https://regengine.co/proof) — download a synthetic FSMA CSV, EPCIS 2.0 JSON-LD bundle, and audit evidence ZIP.
- [regengine.co/verify](https://regengine.co/verify) — drop the public audit bundle into the verifier and confirm file-hash and Merkle-root integrity.
- [regengine.co/proof/recall-drill](https://regengine.co/proof/recall-drill) — call the public recall-drill endpoint against a frozen synthetic dataset and reproduce the case-study metrics.

## Production Spine

```text
ingest source record
  -> preflight in Inflow Workbench
  -> normalize to CTE/KDE shape
  -> score readiness and route fix queue items
  -> pass commit gate
  -> persist tenant-scoped event data
  -> evaluate rules
  -> expose compliance/audit/export views
```

The diagram describes the Workbench workflow. Direct webhook, CSV, EPCIS, and EDI intake has route-specific validation and persistence; it does not universally pass through Workbench. Event persistence is mid-migration from a legacy CTE store to a canonical hash-chain store: some write paths still write both stores, newer paths write canonical-only, and read paths have consumer-specific cutover flags. Chain verification defaults to canonical reads; FDA CSV export v1 retains a legacy code default. Historical rollout observations are recorded in the cutover runbook; current deployment flags must be read back separately (see [docs/persistence/dual-write-cutover.md](docs/persistence/dual-write-cutover.md)). Graph, NLP, generic regulatory-intelligence, and document-ingestion modules are present, but they should not be treated as the core product contract without checking the relevant tests and deploy wiring.

# Repository Purpose

This repository contains the production application for RegEngine.

RegEngine is a pre-production, API-first FSMA 204 food traceability evidence platform. See [the canonical product description](docs/PRODUCT_DESCRIPTION.md) for positioning and capability availability. Its primary job is to ingest supplier and ERP data, normalize it into traceability evidence, validate the evidence against FSMA 204 expectations, and produce audit/export material for regulatory workflows.

## Scope

- Webhook, CSV, EPCIS, and EDI ingestion for FSMA 204
- Inflow Workbench preflight, readiness, fix queues, and commit gates
- Optional CSV column and event-type suggestions, subordinate to deterministic validation
- CTE/KDE canonicalization
- Compliance validation and readiness scoring
- Tenant-scoped data model
- Audit evidence and hash-chain persistence
- FDA-oriented exports, request-response packages, recall readiness, and public synthetic proof
- Supplier correction and remediation workflows, subject to router enablement
- Operator/admin workflows required to manage tenants, users, API keys, and audit logs

## Non-Goals

- Experimental features on the production request path
- Non-FSMA verticals
- Demo-only tooling
- Unbounded generic document or NLP products
- Integrations that bypass tenant isolation, schema validation, or audit evidence persistence

## Production Standard

Code in this repository should be evaluated against the FSMA pipeline:

```text
ingest -> canonicalize -> validate -> persist evidence -> export
```

Changes that do not strengthen or protect that pipeline should be explicitly marked as experimental, archived, or kept outside the production router surface.

## Canonical Event

| | |
|---|---|
| **Definition** | A normalized supply chain traceability event (CTE) with Key Data Elements (KDEs), provenance metadata, content hash, and chain hash. Represents one discrete action in the food supply chain: harvesting, cooling, packing, receiving, shipping, or transformation. |
| **Schema** | `TraceabilityEvent` in `services/shared/canonical_event.py`. Key fields: `event_id`, `tenant_id`, `event_type` (CTEType enum), `traceability_lot_code`, `kdes` (JSONB), `sha256_hash`, `chain_hash`, `status` (ACTIVE/SUPERSEDED/REJECTED/DRAFT), `idempotency_key`, `provenance_metadata`. |
| **Persistence** | `fsma.traceability_events` table (canonical). Legacy: `fsma.cte_events` + `fsma.cte_kdes` (dual-write, to be removed). |
| **Who writes** | Ingestion service, via `services/shared/canonical_persistence/`. |
| **Who reads** | Compliance (rule evaluation), graph (visualization), admin (dashboard), export (FDA artifacts). |
| **Versioning** | Immutable once status=ACTIVE. Amendments create a new event with `supersedes_event_id` pointing to the original, and the original status becomes SUPERSEDED. |
| **Derived vs Canonical** | **Canonical.** This is the source of truth. `cte_events` is a legacy derived copy (dual-write) that will be removed. |

## Canonical Entity

| | |
|---|---|
| **Definition** | A resolved real-world entity in the supply chain: a firm, facility, product, lot, or trading relationship. Carries standard identifiers (GLN, GTIN, FDA registration) plus verification status and confidence score. |
| **Schema** | `CanonicalEntity` in `services/shared/identity_resolution/`.
